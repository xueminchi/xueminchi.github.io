Memory for Robot Policies

Compressing history without losing sight of the present

Xuemin Chi · September 2026 · Team implementations and experimental observations

Overview

A robot can remember the preceding action yet still fail to respond to the current scene. This report examines two practical ways to add visual history to a robot policy: temporal fusion inside a pretrained vision encoder, and learned-query compression after image encoding. It connects their PyTorch implementations to real-robot observations: reduced repeated edge pinching during box folding, but also sensitivity to initial placement and deteriorating performance after multiple cup swaps. These observations motivate a distinction between remembering a sequence and using memory to guide perception-conditioned control.

01 / INTRODUCTION

What must the robot remember?

A single image may not reveal which cup hides a ball after an exchange, or whether a box edge has already been pinched. History can disambiguate these situations. However, a long task does not automatically require memory: some stages can be inferred directly from the current scene. The useful question is which information is missing now, and how long it must remain available.

Raw image history retains appearance but increases computation. Robot-state history is compact, but cannot by itself describe a human moving a hidden object. Text can record counts or completed subtasks, but discards geometric detail. These are different representations of history, not interchangeable forms of the same input.

The implementation comparison below is narrower. It covers a MEM-style video encoder integrated into π0.5, and a separate history resampler built around learned queries. The latter is clip-based: its queries start from the same learned seeds on each call. It is not a recurrent memory bank, and neither implementation should be presented as a reproduction of every component in the systems above.

A. MEM-style temporal fusion inside the vision encoder

History changes the current-image representation; it does not become a separate bank of memory tokens. This path adapts MEM's short-term visual-memory idea to a π0.5 policy. It fuses information across frames inside the vision encoder, then passes only the current frame's updated patch features to the VLM. Unlike B, there is no independent set of learned memory queries and no extra history-token block in the prefix.

Time and space are mixed separately

Temporal attention treats each spatial patch index as a sequence across frames. A causal mask lets a timestep read itself and earlier timesteps, but not later ones. Q, K and V are projections of those image features. The subsequent spatial block mixes different patches within each frame. In this implementation, a temporal-attention residual update precedes the normal spatial block at the selected layers.

A fixed patch index does not track one object as it moves. Spatial and temporal mixing together provide routes for information to travel across locations and time, but do not implement explicit object tracking. The current frame is the latest observation available for the action; the history clip must not contain later observations.

Why can historical tokens be removed?

Before removal, the current frame's patch features have already read historical features through temporal attention. The retained tokens therefore describe the current scene with information from the observed past. This is learned compression, not a guarantee that every past event or detail survives.

Per-camera hidden features: [B, T, P, D_vision]
Keep the current frame after temporal fusion: [B, P, D_vision]
Vision-to-VLM projection: [B, P, D_model]
Prefix: [history-enhanced current-image tokens | language tokens]

Reuse pretrained weights, not a second query bank

The temporal wrapper reuses the selected vision block's normalization and Q/K/V/output projections. Its temporal position encoding is fixed, with zero at the current frame, so the wrapper adds no independent trainable parameter set. The reused weights can still be trained; parameter reuse does not mean frozen weights or memory competence without training. Single-frame input explicitly takes the native image path, although later fine-tuning can still change that path's weights.

Expand PyTorch · causal temporal attention with reused vision weights
def causal_temporal_layer(layer, x):
    """x: [B,T,P,D_vision]; reuse one SigLIP block's norm and Q/K/V/O.
    Q/K/V come from image features, not independent learned memory queries.
    """
    b, t, p, d = x.shape
    positions = torch.arange(t, device=x.device).float() - (t - 1)
    freq = torch.exp(-torch.arange(d // 2, device=x.device).float()
                     * math.log(10000) / max(d // 2 - 1, 1))
    angles = positions[:, None] * freq
    pe = torch.cat([angles.sin(), angles.cos()], dim=-1)
    pe = F.pad(pe - pe[-1:], (0, d - pe.shape[-1])).to(x.dtype)
    z = (x + pe[None, :, None]).permute(0, 2, 1, 3).reshape(b*p, t, d)
    z = layer.layer_norm1(z)
    attn = layer.self_attn
    h, dh = attn.num_heads, attn.head_dim
    q, k, v = [
        projection(z).reshape(b*p, t, h, dh).transpose(1, 2)
        for projection in (attn.q_proj, attn.k_proj, attn.v_proj)
    ]
    y = F.scaled_dot_product_attention(
        q, k, v, is_causal=True, scale=attn.scale,
        dropout_p=attn.dropout if layer.training else 0.0,
    )
    y = y.transpose(1, 2).reshape(b*p, t, d)
    # Attention output projection: stays in the vision feature space.
    y = attn.out_proj(y).reshape(b, p, t, d).permute(0, 2, 1, 3)
    return x + y

The input width here is D_vision. attn.out_proj is the attention module's output projection within that feature space, not the later vision-to-VLM projector. The temporal residual is added before the existing spatial block; this teaching excerpt describes our implementation, not a claim of operator-by-operator equivalence to the authors' internal code.

Expand PyTorch · interleave temporal mixing and retain current-frame tokens
def encode_memory_clip(vlm, clip, every=4):
    """clip: [B,T,3,H,W], oldest first, current frame last.
    Returns [B,P,D_model]; internal hidden width is D_vision.
    Expects a PaliGemma-compatible vision tower and projector.
    """
    if every < 1:
        raise ValueError("every must be positive")
    b, t, c, h, w = clip.shape
    if t == 1:
        return vlm.get_image_features(clip[:, 0])
    tower = vlm.vision_tower.vision_model
    layers = tower.encoder.layers
    x = tower.embeddings(clip.reshape(b*t, c, h, w))
    x = x.to(layers[0].self_attn.q_proj.weight.dtype)
    p, d = x.shape[1:]
    x = x.reshape(b, t, p, d)
    temporal_ids = tuple(range(every - 1, len(layers), every))
    for i, layer in enumerate(layers):
        if x.ndim == 4:
            if i in temporal_ids:
                x = causal_temporal_layer(layer, x)
            x = layer(x.reshape(b*t, p, d),
                      attention_mask=None, output_attentions=False)[0]
            x = x.reshape(b, t, p, d)
            if temporal_ids and i == temporal_ids[-1]:
                # Drop history only after the final temporal + spatial block.
                # For 24 layers and every=4, this is the last vision block.
                x = x[:, -1]
        else:
            x = layer(x, attention_mask=None, output_attentions=False)[0]
    x = x[:, -1] if x.ndim == 4 else x
    # Vision-to-VLM projection: D_vision -> D_model; P tokens remain.
    return vlm.multi_modal_projector(tower.post_layernorm(x))

multi_modal_projector maps D_vision to D_model after the final vision normalization. It changes feature width, not the number P of retained patch tokens. With multiple cameras, this path is applied per camera and their output tokens are assembled by the policy.

What is saved, and what still costs compute?

The main token-count saving is downstream: each camera contributes P visual tokens to the VLM instead of T × P. The historical images still pass through the vision encoder and participate in temporal processing. In the reviewed 24-layer encoder with a four-block interval, temporal mixing occurs at blocks 4, 8, 12, 16, 20 and 24. History is therefore removed after the last vision block in this configuration, not early enough to skip a large stack of upper vision blocks. Constant output token count is not constant total latency.

A finite observation window, not persistent memory

The reviewed box-folding configuration supplies four historical frames and the current frame from each of three cameras. Its target offsets are −6, −4.5, −3, −1.5 and 0 seconds. Views share the target sampling offsets, and frames within a camera clip share augmentation parameters. Actual frame timing and freshness still depend on the observation pipeline; the encoder's time embedding represents frame-slot positions, not sensor timestamps.

Each call re-encodes the supplied clip. There is no recurrent memory state that independently preserves an event after it leaves that window. This short-term visual component should also remain distinct from the complete π0.6-MEM system: our reviewed π0.5 setup does not establish integration of MEM's long-term language memory or reproduction of its full training recipe and results.

B. Two-stream memory: appearance and motion

This path does more than pool historical images. It preserves two complementary token streams before compression: appearance, describing what each patch contains, and motion cues, describing how its features changed between adjacent sampled frames. Both are built from the same encoded image features. The reviewed shell-game and block-building configurations enable the motion branch.

The earlier frame-mean implementation reduced every image to one vector before processing history. The patch-preserving version avoids that early spatial averaging. This retains information about where a visual change occurred, although a patch location is not an object identity or a tracked trajectory.

What comes out of the compressor? Cross-attention returns one vector per learned query. Query and feed-forward residual updates refine those vectors; a final normalization and linear projection map their width from d to the policy width D. The result is M memory tokens of shape [B, M, D]. The query count sets the number of output tokens; the projection changes their feature width, not their number.

What does “policy prefix” mean? It is the concatenated conditioning sequence [current-image tokens | memory tokens | language tokens]. Inserting memory adds history as an input to the policy; it does not itself produce an action or introduce a separate “prefix network.” The policy processes this sequence, and the Action Expert uses the resulting context under its existing attention rules. Current visual observations remain available alongside memory.

What is actually learned?

The input projection, time/space embeddings, two stream-type embeddings, query vectors, attention projections and feed-forward/output layers are trainable. The subtraction itself is fixed arithmetic: the model learns how to represent and use feature changes through the surrounding layers. Appearance and motion share the input projection, time/space embeddings and compressor, but have separate learned type embeddings. This path does not introduce separate appearance and motion supervision losses.

Calling the second branch “motion” describes its intended cue, not a measured optical-flow field. It is a difference between features at the same patch index, with no object correspondence or camera-motion compensation. It can respond to an object moving, but also to a changing camera view or illumination. It adds a useful representation of change, not information absent from the original feature sequence.

How the two streams become memory

After concatenation, each learned query attends jointly to valid tokens from both streams. The queries are neither permanently assigned to appearance versus motion nor allocated one per frame. They select a fixed-size summary of the clip through cross-attention, followed by residual and feed-forward updates. Position embeddings distinguish sampled times and patch locations; the implementation interpolates its learned temporal embedding table when the clip length changes.

Q = learned memory queries; K/V = the joint appearance–motion bank

class HistoryResampler(nn.Module):
    """Appearance/motion token streams, jointly read by learned queries.
    Input [B,T,P,D] -> memory [B,M,D]; no recurrent state.
    """
    def __init__(self, dim, patches, max_frames, memory_tokens=32,
                 width=512, heads=8, use_motion_tokens=True):
        super().__init__()
        self.use_motion_tokens = use_motion_tokens
        self.in_proj = nn.Linear(dim, width)  # Shared by both streams.
        self.time = nn.Parameter(torch.randn(1, max_frames, 1, width) * .02)
        self.space = nn.Parameter(torch.randn(1, 1, patches, width) * .02)
        self.appearance_type = nn.Parameter(torch.randn(1, 1, 1, width) * .02)
        self.motion_type = nn.Parameter(torch.randn(1, 1, 1, width) * .02)
        self.queries = nn.Parameter(torch.randn(1, memory_tokens, width) * .02)
        self.q_norm, self.k_norm = nn.LayerNorm(width), nn.LayerNorm(width)
        self.attn = nn.MultiheadAttention(width, heads, batch_first=True)
        self.ff_norm = nn.LayerNorm(width)
        self.ff = nn.Sequential(nn.Linear(width, 4*width), nn.GELU(),
                                nn.Linear(4*width, width))
        self.out_norm = nn.LayerNorm(width)
        self.out_proj = nn.Linear(width, dim)

    def _time_embedding(self, length, like):
        pos = self.time.squeeze(2)
        if length != pos.shape[1]:
            pos = F.interpolate(pos.transpose(1, 2).float(), size=length,
                                mode="linear", align_corners=False).transpose(1, 2)
        return pos.unsqueeze(2).to(device=like.device, dtype=like.dtype)

    def _token_bank(self, patches, valid_frames):
        b, t, p, _ = patches.shape
        valid = valid_frames.to(device=patches.device, dtype=torch.bool)
        z = self.in_proj(patches)
        pos = self._time_embedding(t, z) + self.space

        # Appearance: preserve what each spatial patch contains.
        appearance = z + pos + self.appearance_type
        streams = [appearance]
        masks = [valid[:, :, None].expand(-1, -1, p)]

        if self.use_motion_tokens:
            # Motion cue: difference BEFORE adding positions/type embeddings.
            delta = torch.zeros_like(z)
            delta[:, 1:] = z[:, 1:] - z[:, :-1]
            motion = delta + pos + self.motion_type
            pair_valid = torch.zeros_like(valid)
            pair_valid[:, 1:] = valid[:, 1:] & valid[:, :-1]
            streams.append(motion)
            masks.append(pair_valid[:, :, None].expand(-1, -1, p))

        # Two streams are concatenated, not summed or pooled independently.
        values = torch.cat(streams, dim=2).reshape(b, -1, z.shape[-1])
        mask = torch.cat(masks, dim=2).reshape(b, -1)
        return values, mask

    def forward(self, patches, valid_frames):
        values, mask = self._token_bank(patches, valid_frames)
        empty = ~mask.any(dim=1)
        mask = mask.clone()
        mask[empty, 0] = True  # Avoid all-masked attention producing NaNs.
        q = self.queries.expand(patches.shape[0], -1, -1).to(values)
        pooled, _ = self.attn(self.q_norm(q), self.k_norm(values), values,
                             key_padding_mask=~mask, need_weights=False)
        memory = q + pooled
        memory = memory + self.ff(self.ff_norm(memory))
        memory = self.out_proj(self.out_norm(memory))
        return memory.masked_fill(empty[:, None, None], 0)

This teaching version keeps the shared projection, separate stream types, optional motion branch, temporal-position interpolation and joint attention from the reviewed implementation. It additionally zeroes all-invalid output rows; the policy must mask those rows as well. It omits shape guards and training/runtime setup, and uses simplified parameter initialization.

Every appearance token needs one valid frame; every motion token needs two adjacent valid frames. The first difference has no predecessor and is masked. Queries can read the complete observed clip because the resulting memory conditions an action after that clip; training must still exclude observations from after the action's observation time. Each call starts from the same learned query seeds, not a recurrent state carried from the previous call.

Capacity and implementation limits

For one 224 × 224 view with 256 patches and 50 history frames, the appearance stream has 12,800 tokens. Enabling motion creates a bank of 25,600 token slots; with all 50 frames valid, 25,344 are valid because the first 256 motion slots are masked. The reviewed configurations use a 512-wide bottleneck and either 32 or 512 output queries. These are implementation settings, not evidence that one setting is optimal.

The audited configurations use head-camera history. The integration averages corresponding encoded patch features if multiple history cameras are supplied, so this version should not be described as preserving distinct multi-view geometry. Current-camera images are processed separately. Compression bounds the history prefix length, but still requires historical image encoding and attention over the two-stream bank; token counts are not measured latency or speedup results.

C. Let the policy use the memory

The history resampler's output is inserted between current-image tokens and language tokens in the VLM prefix. The existing policy attention rules then determine how the Action Expert reads the prefix. This is different from concatenating a pooled vector to robot state or injecting it through adaptive normalization.

Expand PyTorch · assemble the conditioning prefix
def build_prefix(current_images, memory, language,
                 image_valid, memory_valid, language_valid):
    """All tokens are projected to the same feature width.
    True means valid in returned padding mask.
    """
    tokens = torch.cat([current_images, memory, language], dim=1)
    valid = torch.cat([image_valid, memory_valid, language_valid], dim=1)
    # Feed these to the policy's existing prefix/Action Expert interface.
    # The policy must still construct its own prefix-to-action attention mask.
    return tokens, valid

This excerpt only constructs tokens and validity masks. It does not replace the policy's attention-mask logic, position IDs, normalization or action-generation path.

Text memory serves a different role. A separate high-level implementation predicts the next subtask and an updated language memory, such as the number of cubes already placed. Its evaluation must distinguish supplying correct previous memory from feeding the model's own predictions back. That high-level route is not claimed here to have been integrated with the visual-memory controller into one evaluated robot system.

03 / REAL-ROBOT OBSERVATIONS

Less repetition does not guarantee better grounding

Box folding: an improvement and a limitation

The experiment notes report that repeated pinching of the box edge was not observed in this MEM run, whereas repeated pinching had been seen without memory. The available video provides an illustrative execution, but no matched no-memory clip or trial count is available for a quantitative comparison.

The same notes record a loss of sensitivity to the initial box position: the grasp did not adjust adequately when the box was moved. They also describe the robot continuing the action routine on an empty table. The empty-table recording is not embedded here. These failures matter even if the nominal folding sequence looks smoother.

Is this simply overfitting?

Overfitting is a plausible explanation, not an established diagnosis. Repeating a familiar routine despite a changed scene is consistent with weak dependence on current visual evidence. It could reflect a narrow training distribution, use of history or proprioception as a shortcut for task phase, or a problem in observation delivery or preprocessing. The existing records do not isolate these alternatives or establish a checkpoint-by-checkpoint deterioration.

The MEM paper discusses causal confusion in memory policies and connects robustness to diverse pretraining data. Its post-training-only variant is also weaker than its pretrained memory model. This makes training regime relevant to our observation, but does not establish its cause or exonerate the memory design.

A useful next check would hold the checkpoint and robot state fixed while changing the current image, then hold the current image fixed while changing history. Earlier/later checkpoints and a moved-object scene can help distinguish a memorized routine from a history-input problem. These are proposed diagnostic comparisons, not experiments already completed for this report; any real-robot follow-up requires its normal safety controls.

Shell game: performance drops as swaps accumulate

Operator feedback reports relatively strong performance after one cup swap, but substantially poorer performance after two or three. Without counts and a fixed protocol, no percentages or benchmark score are reported. The observation should remain separate from results in published RoboMME or other evaluation suites.

The failure could involve missed swaps between sampled frames, an event falling outside the history window, loss of object identity during compression, or insufficient examples of longer swap sequences. Simply increasing the number of memory tokens would not establish which explanation is correct.

Takeaway. A compact memory interface is implementable, and the box-folding case offers a useful qualitative result. The unresolved question is whether the policy uses history together with current evidence, rather than as a way to replay a familiar action sequence. The present evidence supports an implementation report and a limitations discussion—not a claim of general memory competence.

Evidence boundary: source/configuration review, archived experiment notes, one supplied box-folding video and qualitative operator feedback. No complete success-rate protocol or isolated encoder-latency measurement is available here. This report therefore does not claim 100% task success or sub-300 ms inference.
