Robot learning / Training systems

Where Robot Training
Slows Down

Video-data locality, communication topology, and recovery that resumes the right samples.

Xuemin Chi · September 2026 · Training-system experiments with π0.5

The question

A robot training job can spend too long waiting even when its model fits comfortably in GPU memory. Is the bottleneck fetching video, revisiting the same frames, synchronizing gradients, or reconstructing progress after a restart? I investigated these boundaries separately. In the recorded experiments, a locality-aware data order improved object-storage training throughput by about 34%; correcting the network-adapter configuration improved cross-node throughput by 31–34%. A recovery test exposed a different distinction: resuming the correct data sequence is not the same as reproducing every floating-point bit.

My contribution: designing and integrating data-order and progress handling, tracing data and communication bottlenecks, and validating changes through controlled training experiments. The focus is training-system performance and correctness; policy quality was not measured.

01 / THE DIAGNOSTIC QUESTION

Which boundary holds up the next update?

Robot samples are not independent image files. A sample can combine several camera streams, a robot-state observation and a future action sequence. Nearby samples often share video frames or decode dependencies. A sampling order that looks harmless at the tensor level can create expensive reads at the storage level.

I separated three questions: can the input path supply batches at the rate the model consumes them; does adding a network boundary expose gradient-synchronization overhead; and after interruption, does the job continue from the data that actually contributed to saved state?

Data → batchStorage reads, video decode and worker locality. Measure input wait alongside complete training steps.
Gradients → updateGPU and network-adapter placement. Verify the transport actually used by the collective.
Update → checkpointSaved model state and consumed sample position must describe the same point in the run.

The comparisons below run actual π0.5 training: forward pass, backward pass and optimizer update, with one training process (called a rank) per GPU. They are separate experiments with different batch sizes and data configurations. Their percentages should not be multiplied into one claimed speedup.

02 / DATA LOCALITY

The median step was fine. The tail was not.

In an eight-GPU comparison, object storage and a parallel file system had nearly identical median step times: around 1.43 seconds. But with global-random sample order, object storage produced much slower tail steps—a 95th-percentile (P95) step time of 4.88–5.09 seconds. Looking only at the median would have missed the problem.

An isolated loader investigation supplied a useful clue: consecutive requests handled by a worker almost never stayed in the same episode. The decoder cache had little chance to help. The full training comparison then showed periodic data waits around worker-prefetch boundaries. That suggested changing the access pattern before adding more workers.

Shuffle larger units, preserve nearby work

I introduced an explicit episode/window order: shuffle episodes and short physical windows, but keep rank-local batches close in the recording. This gives reads and decoder state an opportunity to be reused. The change was in sample scheduling, not a requirement to make every training sample a separate file.

The implementation checked ownership, not just speed: equal batch counts across ranks, deterministic order for a fixed seed and epoch, no repeated sample ownership, and only the declared final incomplete global batch dropped. A separate full-epoch metadata check assigned 1,331,264 samples once and dropped 12; approximately 99.8% of rank-local batches were contiguous within one episode. This checked the complete order plan, not a full epoch of GPU training.

32.61 → 43.66 samples/s  |  +33.9% throughput

The baseline is the mean of both object-storage random-order trials, not the slower trial alone. The corresponding mean P95 fell from 4.982 to 1.665 seconds, a 66.6% reduction. With locality-aware order, object storage and the parallel file system were effectively tied in this short comparison.

Locality is also a statistical choice. Preserving coverage does not preserve the joint distribution of samples within a batch. Nearby robot frames are correlated. This establishes a systems improvement, not unchanged convergence or better policy quality; those require a separate, matched training comparison.

Implementation idea · separate data selection from execution order

The source mixture decides which data enter an epoch. An order planner assigns the selected work to ranks and windows. The reader constructs observations and actions; a model adapter produces policy-specific tensors. These should not become one model-specific dataset class.

# Conceptual pipeline, not executable production code.
selected_work = select_sources(snapshot, mixture, epoch)
order = plan_local_windows(selected_work, seed, world_size)

# Preserve membership; change execution order explicitly.
check_disjoint_rank_ownership(order)
check_equal_rank_batch_counts(order)
check_declared_drop_last(order)

for request in order.for_rank(rank):
    sample = reader.read_window(request)
    batch = model_adapter(sample)
    train_step(batch)

Source proportions and physical locality are separate choices. Window size and shuffle granularity remain learning-relevant parameters; this is not an equivalent of independent global shuffling.

03 / COMMUNICATION TOPOLOGY

Correcting the network configuration recovered throughput.

The next experiment kept eight GPUs in total, but placed four on each of two machines. Throughput fell to about 74% of the single-node reference even though measured input wait stayed below 0.04%. Data loading was unlikely to explain this particular gap.

PyTorch DistributedDataParallel (DDP) replicates the model and synchronizes gradients. I first checked unnecessary parameter-discovery work. Disabling that traversal changed two-node throughput by only about 1.3%—too little to explain the slowdown.

Here, a network adapter means a physical network card, not a neural-network Adapter. The cards support remote direct memory access (RDMA), used for cross-machine communication. Both relevant cards were already installed in each machine; this experiment added no GPUs or network hardware.

The topology inspection showed that, on each node, one GPU pair was near one network card and the other pair was near another. But the configuration restricted communication to one RDMA network card per node, forcing some GPUs onto a more distant path. I removed that restriction and allowed both appropriate cards through NCCL_IB_HCA. This setting filters the interfaces available to NCCL, the GPU communication library; it does not itself prescribe a universal per-GPU route. [1]

Throughput increased from 16.38 to 21.51 samples/s; the repeat reached 21.93. These are gains of 31.3% and 33.9% over the restrictive one-card configuration. Both corrected runs approached the single-node eight-GPU reference of 22.25 samples/s. Communication logs confirmed RDMA transport rather than a silent fallback to ordinary socket communication.

The result supports a topology diagnosis, not a new communication algorithm. The useful lesson is to check whether the configured network path matches GPU placement. The 31–34% gain belongs to this restrictive configuration; it is not a general benefit of enabling a second card.

Why I did not immediately switch to FSDP

Peak allocated memory during training was about 32.8 GiB per 80-GiB GPU. Fully Sharded Data Parallel (FSDP) distributes parameters, gradients and optimizer state across GPUs to reduce memory use. Memory pressure was not the immediate bottleneck here, and switching to FSDP would change communication patterns before resolving the demonstrated routing problem. FSDP itself was not benchmarked.

A subsequent two-node, sixteen-GPU test ran for 300 steps and delivered 39.93 samples/s. With batch per GPU held at two, this is 89.72% weak-scaling efficiency: 39.93 divided by twice the matched eight-GPU reference of 22.25 samples/s. The first 20 steps and all checkpoint-writing cost were excluded. This is a bounded throughput result, not an end-to-end production capacity estimate.

04 / RECOVERY SEMANTICS

A prefetched batch is not a completed update.

A loader may read far ahead of training. Saving its furthest read position would skip data that never contributed to the checkpointed model; restarting the epoch would repeat consumed data. Instead, the saved position must identify the next batch after the work represented by the checkpoint.

I tested this with a real sixteen-GPU control: four continuous steps versus two steps, a checkpoint, new processes and two resumed steps. The plan contained 128 unique samples with no cross-rank overlap. The committed sample position, scheduler state, optimizer structure and Torch CPU/CUDA random states were recovered.

The data sequence matched; the final tensors were not bitwise identical. Step-four losses were 0.05378731 and 0.05378317. The maximum absolute model-weight difference was about 1.22 × 10−4. This supports numerical recovery in a short systems test, not strict replay or equivalent long-run learning.

The audit also found rank 0's Python random state differed after loader creation. Restoring state before constructing workers can allow startup to consume it again. This remained an open correctness issue in the recorded test, especially for future main-process stochastic transforms. Low-precision distributed arithmetic is another possible source of differences; the experiment did not isolate the cause of every unequal tensor. PyTorch also distinguishes reproducibility controls from performance-oriented execution. [2]

Python · a minimal committed-progress invariant
from dataclasses import dataclass

@dataclass
class Progress:
    order_id: str
    next_batch: int = 0

    def complete(self, batch_id):
        if batch_id != self.next_batch:
            raise ValueError("Commit batches in their planned order")
        self.next_batch += 1

05 / WHAT CARRIES FORWARD

Optimize the boundary you can demonstrate.

The common thread is not a file extension or a larger GPU count. It is making the relevant state visible: which video windows a worker revisits, which network path gradients take, and which batches contributed to a checkpoint.

For data, I would keep selection independent of physical ordering and evaluate the learning cost of stronger locality. For communication, I would keep a matched single-node control and inspect the actual transport before changing frameworks. For recovery, I would test sample identity separately from floating-point equivalence, because one can pass while the other fails.

The resulting design separates three responsibilities: selecting training data, scheduling its physical reads, and recording completed work. That separation makes performance changes easier to test without silently changing data coverage or restart behavior. The next validation step is a longer run with checkpoint writes and matched learning metrics.

No shared-server page-cache flush was performed, so these are not controlled cold-cache benchmarks. The short optimized pair does not establish a statistically significant difference between storage backends.

Two efficiency percentages; two different denominators

Placement: two nodes × four GPUs versus one node × eight, same global batch. The two-card observations achieve 21.5084 / 22.2523 = 96.66% and 21.9321 / 22.2523 = 98.56% of the reference.

Weak scaling: two nodes × eight GPUs versus one node × eight, fixed batch per GPU. The 300-step run achieves 39.9290 / (2 × 22.2523) = 89.72%. Global batch increases from 16 to 32. Checkpoint-writing cost is excluded. The earlier 24-step run reached 96.56%; the main text uses the longer observation.

The separate 60K-step folding-task run used an older single-source path. It is not evidence that the later multi-source implementation completed an equivalent long run, and is deliberately excluded from these figures.

Limits and the next validation step

The results cover the recorded 8- and 16-GPU configurations, not hundred-GPU operation, cluster-wide storage behavior or a model scaling law. A later data-path revision on a different node pair did not pass its RDMA throughput validation; these historical numbers do not describe that revision.

Stronger claims need longer multi-node runs with checkpoint writes and restart events, varied video access patterns and object-store contention, matched learning comparisons of sample-order policies, and renewed transport validation on the intended hardware.
