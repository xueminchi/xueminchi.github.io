Robot learning / Data systems

From Robot Recordings
to Training Samples

Designing the data interface between robot collection and policy learning.

Xuemin Chi · September 2026

Two data sources. One tested training path.

ABC-130K and AgiBot expose different camera timing, robot fields and video layouts. I designed and implemented a shared MCAP training view, with explicit source mappings and a separate model-input adapter. The goal was to make those differences inspectable before they reached the learning target.

Outcome: a 634-episode snapshot passed integrity and indexed-read checks; mixed-source samples were reproducible across repeated worker runs, and the path supported real π0.5 training updates. The validation also exposed incorrect index-based alignment and instruction-boundary risks that file-format checks alone would miss.

My contribution: defining collection and training-data requirements, designing the ingestion/reader/model interface, implementing the common data path, and building the correctness checks. Collection planning and the implemented training path are distinguished below.

THE TRAINING PROBLEM

Opening both datasets was not enough.

A policy sample combines images, state, an instruction and future actions. A common file extension does not tell us whether those components describe the same moment or task. In one inspected ABC episode, 1,300 control rows corresponded to 1,294 packets per camera. Pairing them by row number would silently change the observation/action association.

I approached this as a training-interface problem: which source facts must survive conversion, which choices belong to the model, and how can each resulting sample be checked? Those questions led to three design decisions.

DECISION 1 / DATA LIFECYCLE

Preserve recordings. Version the training view.

I kept the original recordings unchanged and generated a separate view for training access. Ingestion performs the conversion, validation and indexing once; workers read its checked outputs. This lets the encoding or index evolve while preserving the source information needed to rebuild or audit a dataset.

ABC's fixed-GOP training video and Dyna's modality-specific MCAP grouping informed different parts of the design. [1] [2] [3] I used a common H.264 access profile and separate camera/control groups: sparse image requests and longer action windows should not force the same storage reads.

The tradeoff: ingestion pays conversion time and additional storage in exchange for a consistent reader path. In the three-episode-per-source calibration, ABC shrank while AgiBot grew. Capacity estimates therefore stayed source-specific; a pooled average would have hidden the cost.

A later metadata/index revision reused the existing video and control payloads. That was a concrete benefit of separating the stored data from its access metadata: a new index did not require another video conversion.

DECISION 2 / MODEL INTERFACE

Share the reader, not every policy assumption.

I kept field definitions, clocks and source provenance in the storage layer. The training recipe selects observations and commands, their time relationship, valid task intervals and action horizon. A separate adapter performs policy-specific normalization, image transforms, padding and tokenization.

This matters across embodiments. The tested joint recipe handles ABC's 14-value state/action layout and AgiBot's 16-value joint/gripper layout through explicit mappings. Matching tensor width does not make their gripper units, joints or coordinate frames equivalent.

The design choice: PI0.5-specific transforms live outside the physical reader. The tested integration uses PI0.5; the replaceable interface is what permits future model recipes without making one policy's tensor format the permanent storage format.

The logical episode may reference immutable payload objects. End-effector pose recipes need their own coordinate-frame and action-semantic checks; the joint-policy tests do not establish those conversions.

DECISION 3 / LEARNING TARGETS

Validate the observation/action relationship.

For the inspected ABC source, I used the latest declared camera timestamp at or before a control anchor. Control row 0 selected frame 4; row 650 selected frame 648. Near the end, top and wrist cameras selected different indices. Neither equal-index matching nor a fixed offset described the recording correctly.

The recipe also checks the future target: an action chunk must remain inside its selected instruction segment. In one audit, 634 stored episodes yielded 632 recipe-eligible episodes because two lacked the required committed intervals or annotations. Those source recordings remained in the inventory; the recipe did not invent missing instructions.

The learning consequence: a perfectly decodable image can still be paired with the wrong state or a target from the next task. Sample validity has to include time and instruction boundaries, not just file integrity.

Camera selection uses the source's declared timing rule. The tested AgiBot view instead binds a validated ordinal-alignment rule. In either case, clock comparability and timestamp meaning must be established separately; recording time is not automatically sensor exposure time. [4]

Python · an explicit causal-selection rule
from bisect import bisect_right

def camera_at_or_before(times_ns, anchor_ns, max_age_ns):
    # Caller has validated a nonempty, strictly increasing time index,
    # comparable clocks, and a common valid camera/control interval.
    i = bisect_right(times_ns, anchor_ns) - 1
    if i < 0 or anchor_ns - times_ns[i] > max_age_ns:
        raise ValueError("No valid causal camera observation")
    return i

# Frame choice, future-action offset and task boundaries are separate:
# image = camera_at_or_before(camera_times, control_time, tolerance)
# actions = commands[t + offset : t + offset + horizon]
# Reject a window that crosses the selected instruction segment.

Teaching code, not the full production reader. The retained implementation batches lookups with numpy.searchsorted(..., side="right") - 1; this example makes the additional freshness requirement explicit. The selected AgiBot view has a different, declared ordinal-alignment rule. A single rule is not imposed blindly on both sources.

Indexing result · choose the frame without reading the video

The first reader scanned encoded packet envelopes to build camera time arrays. Moving the same lossless arrays into a content-bound index removed those scans. In one warm CPU comparison, the index grew from 5,733 to 9,535 bytes; the three initial lookups fell from about 211 ms to 79 µs, with identical selected frames.

This measures metadata lookup only, not video decode or training speed. The design benefit is the removed dependency: a time lookup no longer needs video payload access.

RESULTS AND SCOPE

From converted files to real training updates.

The common snapshot contains 360 ABC and 274 AgiBot episodes, about 61.1 GB. I verified all camera/control payload hashes and exercised an indexed read in every episode. Separate tests checked source decoding, conversion quality, repeated model inputs and actual policy updates.

What these results establish

A working, bounded ingestion-to-training implementation. Exact source preservation, lossy conversion tolerance and repeated-sample equality were tested separately. Full payload hashing is not exhaustive decoding, and image-error thresholds are not evidence of policy-quality gains.

The latest training-path changes still need integration, broader production-load/recovery testing and matched policy evaluation. The short 16-GPU TCP run passed functionally, not the high-throughput acceptance target. This report does not claim a company-wide platform deployment or million-hour validation.

Training throughput and communication tuning are covered in a separate report. Here, the result is a checked common data path that those performance experiments can build on.

BACK TO COLLECTION

Turn training failures into collection requirements.

The same analysis informed the collection specification: distinguish measured state from commanded targets; bind calibration versions, coordinate frames and units; preserve task identity and completion status. These requirements give collection and data-platform teams concrete information to record and verify.

For example, an anonymized raw episode fully parsed and decoded, yet its video and robot timestamps had different relationships to recording time. I documented the ambiguity for follow-up rather than assigning a corrected timestamp without evidence.

Collection evidence · one raw audit and the task-card plan

The raw audit parsed 31,928 messages and decoded all 2,150 video frames. Video message timestamps were about 0.87 seconds earlier than recording time; robot feedback differed by only a few milliseconds. Some teleoperation-target timestamps repeated or predated the episode. The cause and clock mapping remain unresolved: this is not a measured physical latency or synchronization error.

The collection plan contains 54 candidate task templates and eight example task cards, covering object/scene variation, success criteria and grouped train/evaluation separation. This is design work, not a claim that those tasks have already been collected. The cards and raw-data requirements have different maturity from the implemented ABC/AgiBot input path.

The contribution across the project: connecting what the robot records to what the policy learns. I translated source differences into explicit interfaces and tests, implemented the shared path, and used the failures to sharpen collection requirements.

IMPLEMENTATION NOTES

Details behind the design decisions.

Code excerpts and calibration results for a deeper technical discussion. The teaching examples are simplified and are not a standalone production pipeline.

Video conversion · encoding, storage groups and cost

A group of pictures (GOP) describes a keyframe and dependent video frames; a MCAP chunk is a storage block containing messages. Locating a chunk does not eliminate video decode dependencies.

Encoding

H.264, output playback clock 30 FPS, fixed GOP30 and B=0 for the tested view.

Grouping

Camera messages share one access group; dense observations and commands use another.

Indexing

Source-time and keyframe indexes are built during ingestion, before workers request samples.

ABC's efficient training implementation uses MP4; I borrowed its predictable video-access profile, not the container choice. Dyna informed the grouped MCAP layout and distinguishes sparse VLA windows from longer contiguous world-action reads. [2] [3] The chosen B=0/GOP30 profile is specific to this training view, not a MCAP requirement or a universal world-action-model setting.

Implementation detail · an encoder option was not enough

The first strict GOP test still found extra keyframes after scene-cut detection had been disabled. Decoded frames carried source picture-type hints into re-encoding. Clearing those hints allowed the output keyframe schedule to be controlled by the new encoding profile.

# Simplified excerpt: encoder configuration and validation omitted.

for ordinal, frame in enumerate(prepared_frames):

for packet in encoder.encode(None):  # flush delayed output

These generated video timestamps describe the output playback clock. They do not replace source sensor times, which remain separately indexed. Production code also validates frame counts, the keyframe schedule, packet timing, color interpretation and source-to-output image tolerance.

The three-episode-per-source calibration produced aggregate ratios of 0.883× for ABC and 2.042× for AgiBot. Their combined ratio of almost 1.00× was an accidental cancellation, not a capacity-planning rule. These are whole conversion-pipeline ratios, not isolated B-frame effects.

Repeatable ingestion · memory, content identity and publication

An early writer streamed decoded frames but still retained every encoded payload in a Python list. I changed it to spool encoded bytes to temporary files and merge streams using positional reads. Small descriptors and indexes remain in memory; the change bounds payload accumulation rather than making total memory constant.

Another test produced identical camera/control/index bytes but unequal manifest hashes: processing time had been included in the manifest. I moved runtime telemetry outside dataset identity. Source hashes, transform versions and content hashes describe data; host names and elapsed times describe a job.

Publication logic · incomplete output must not become a dataset
# Conceptual protocol, not a portable filesystem transaction.

# A local rename and an object-store publication are different operations.

The implementation uses episode-level partial output and verified reuse after interruption. Publication is validated separately by a reader through another access path. Neither a checksum nor a completion marker proves that the robot action labels are semantically correct.

The full snapshot verification hashed all 634 payload pairs and sampled indexed control/camera reads per episode. After publication, an independent reader rechecked three episodes from each source, including decoding. A later metadata/index revision reused the immutable payloads.
