Practical π0.5 Training Acceleration

torch.compile, fused AdamW, and an 80K-step run on A800 GPUs

Xuemin Chi · September 6, 2026

A small training-stack change reduced steady-state step time from 2.57 to 1.60 seconds in a matched two-A800 comparison. A subsequent eight-A800 run completed 80,000 updates at approximately 1.6 seconds per step. This note covers the implementation, the measured gain, and the difference between warm training throughput and total runtime.

What changed

The work targeted an existing PyTorch π0.5 training pipeline for dual-arm garment folding. Building on the team’s acceleration branch, I integrated and validated an optional fast path without changing the model architecture or the data recipe used in the two-GPU comparison.

  • Compile the training model. Apply torch.compile(model) in default mode. In this implementation, compilation wraps the model after DistributedDataParallel (DDP); it does not compile the data loader or the entire training loop. See the PyTorch compile API.
  • Enable fused AdamW. Use the optimizer’s fused=True path. This is a separate optimization, so the measured speedup belongs to the combined configuration, not compile alone. See the AdamW API.
  • Preserve training compatibility. Unwrap DDP and compile wrappers when saving or loading model weights, retain the eager fallback, and provide explicit launch switches. Gradient checkpointing remained enabled in both comparison runs.
# Keep the existing optimizer hyperparameters.
optimizer = torch.optim.AdamW(
    model.parameters(),
    **optimizer_kwargs,
    fused=True,
)

# Compile the training model using the default mode.
model = torch.compile(model)

Simplified core snippet: optimizer_kwargs contains the original optimizer hyperparameters, and model is already DDP-wrapped for multi-GPU training. The full integration also unwraps DDP and compile wrappers when saving or loading weights; configuration switches and that compatibility code are omitted here.

Two GPUs: measuring the gain

Both runs used two A800 GPUs, the same garment-folding configuration, global batch 32 (16 samples per GPU), and 100 optimizer updates. Checkpoint writes were disabled for this short comparison.

Matched two-A800 comparison
Training configurationSteady step time100-step elapsed time
Eager + ordinary AdamW2.57 s4 min 36 s
Compile + fused AdamW1.60 s10 min 51 s

This is a 37.7% reduction in steady step time, or 1.61× throughput. Steady values are medians of the progress-bar estimates at steps 30–90, with repeated entries removed. Elapsed-clock differences over the same interval independently give 2.583 and 1.600 seconds per update.

The compiled run was nevertheless slower over just 100 steps: its first update took approximately 297 seconds, and another 185-second pause occurred near step 94. The log does not establish the precise cause of that later pause. Short-run wall time and steady throughput therefore answer different questions.

Eight GPUs: verifying sustained training

A subsequent run used 8×A800-SXM4-80GB, global batch 128, and BF16, with PyTorch 2.7.1. The policy consumed three camera views and predicted 50-step action chunks. Compile, fused AdamW, and gradient checkpointing were enabled throughout.

The run completed all 80,000 updates and saved the final checkpoint. After step 1,000, the median of 790 hundred-step timing windows was 1.579 s/update. The complete training-loop elapsed time was approximately 36.96 hours, averaging 1.663 s/update, including startup within the loop and later stalls or saves.

This is evidence of sustained use, not a second matched speedup experiment: the eight-GPU run used a later dataset version and has no paired eager baseline in the audited record. Timings are training-loop wall time, not isolated model-forward latency, and exclude setup before the loop.

The practical takeaway

The useful result is not merely that a compiler flag can be enabled. It is that a measured fast path can be integrated with distributed training, ordinary weight files, and long-running jobs. Here, the two-GPU comparison establishes a steady-state gain; the eight-GPU run demonstrates approximately 1.6-second training steps over a completed 80K-update job.

For this workload, compile plus fused AdamW was a useful training optimization. The next comparison should keep the optimizer fixed to isolate compile’s contribution. These timing results do not claim improved policy quality or inference speed.

Evidence: archived May–June 2026 training logs, launch configurations, Git history, and experiment metadata, audited in September 2026. No new training run was performed for this note; private source files and raw logs are not included.
